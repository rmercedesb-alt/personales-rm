1. Contexto y Alcance para Claude Code
Claude Code debe construir un sistema completo de administración de inmuebles usando un único Google Sheet con múltiples pestañas como base de datos, y Google Apps Script (GAS) como motor de lógica. El sistema debe replicar, en la medida que la plataforma lo permita, el modelo definido en el Sistema v3.0.
Lo que Claude Code debe construir
Un Google Sheet con exactamente las pestañas definidas en la Sección 3, con los encabezados, formatos y validaciones especificados.
Un proyecto de Google Apps Script vinculado al Sheet con todas las funciones descritas en las Secciones 4 y 5.
Un menú personalizado en el Sheet ('⚙ Admin Inmuebles') desde donde el administrador ejecuta todos los procesos.
Triggers automáticos de Apps Script: diario (mora y CxC), por edición (validaciones), y por tiempo (avisos).
Funciones de carga inicial de datos (migración) para ingresar CxC activas y pagos históricos.
Protecciones de rango por rol: Administrador, Asistente de cobros y Solo lectura.
Generación de reportes en una pestaña dinámica y exportación a PDF via Google Drive.
Limitaciones conocidas vs. v3.0 (Claude Code debe documentarlas en el Sheet)
Mapa interactivo: Google Sheets no soporta Mapbox/Google Maps embebido con marcadores dinámicos. Alternativa: fórmula 
IMAGE(
) con Google Maps Static API para mostrar la ubicación de un inmueble individual al seleccionarlo.
WhatsApp Business API: Apps Script no puede llamar directamente a la API de Meta sin un webhook intermediario. Alternativa implementada: generación de links wa.me con el mensaje pre-formateado para envío manual con un clic, y opcionalmente integración con Make.com/Zapier si el cliente tiene cuenta.
Hash SHA-256 en PDFs: no disponible en Apps Script nativo. Los PDFs de cierre y liquidación se generan vía Google Docs template y se exportan a Drive sin hash.
Roles granulares: se implementan con protecciones de rango de Google Sheets. No son tan robustos como JWT, pero son funcionales para 3–5 usuarios.
Transacciones atómicas: Apps Script no tiene rollback. Las operaciones críticas (cuadre, liquidación) deben ser idempotentes y registrar su estado antes de ejecutar.

4.4 Función: registrarPago(datos)
Lógica de registro de pago
Validar que el ID_CXC existe y no está en estado PAGADO o ANULADO.
Obtener o crear la sesión de caja del día. Si no existe sesión ABIERTA para hoy, crear una nueva con ESTADO = ABIERTA.
Aplicar el pago: primero a mora pendiente, luego al principal.
Calcular nuevo MONTO_PAGADO = suma anterior + monto recibido.
Calcular nuevo SALDO_PENDIENTE = MONTO_TOTAL - MONTO_PAGADO.
Actualizar ESTADO del CxC: si SALDO_PENDIENTE &lt;= 0 → PAGADO (registrar FECHA_PAGO_TOTAL); si SALDO_PENDIENTE &gt; 0 → PARCIAL.
Insertar fila en CXC_PAGOS con ESTADO_CUSTODIA = COBRADO, ID_SESION_CAJA = sesión activa.
Insertar fila en LOG_CUSTODIA: evento = REGISTRO_PAGO, estado_anterior = NULL, estado_nuevo = COBRADO.
Actualizar totales de la sesión de caja (TOTAL_EFECTIVO, TOTAL_TRANSFERENCIA, etc. según forma de pago).
Llamar a generarReciboPDF(id_pago) para generar el recibo.
Llamar a 
generarLinkWhatsApp(
id_pago, tipo='PAGO_CONFIRMADO') para preparar el aviso.
Actualizar el Dashboard.

Proceso de cuadre

Validar que la sesión existe y está en estado ABIERTA o PENDIENTE_AJUSTE.
Leer todos los pagos en CXC_PAGOS con ID_SESION_CAJA = id_sesion y ESTADO_CUSTODIA = COBRADO.
Para cada pago: actualizar ESTADO_CUSTODIA → EN_ADMINISTRACION y FECHA_EN_ADMINISTRACION → ahora.
Para cada pago: insertar fila en LOG_CUSTODIA: evento = CUADRE_CAJA, estado_anterior = COBRADO, estado_nuevo = EN_ADMINISTRACION.
Actualizar la sesión: ESTADO → APROBADA, USUARIO_CIERRE = email del admin, FECHA_CIERRE = ahora.

Actualizar el Dashboard.
4.6 Función: 
procesarLiquidacion(
id_propietario, fecha_desde, fecha_hasta, filtro_adicional)
Proceso de liquidación
Validar que el usuario tiene rol Administrador.
Leer todos los pagos en CXC_PAGOS donde ID_PROPIETARIO = id_propietario AND ESTADO_CUSTODIA = EN_ADMINISTRACION AND FECHA_EN_ADMINISTRACION entre fecha_desde y fecha_hasta (y filtro_adicional si aplica).
Si no hay pagos que cumplan el criterio, mostrar alerta y detener.
Calcular: total_cobrado = suma de MONTO_PAGADO, total_mora = suma de APLICADO_A_MORA.
Obtener esquema de comisión del propietario (o del contrato si sobreescribe). Calcular comision_administrador.
Calcular monto_neto = total_cobrado - comision_administrador.
Crear registro en LIQUIDACIONES con estado PENDIENTE.
Para cada pago incluido: actualizar ESTADO_CUSTODIA → LIQUIDADO, ID_LIQUIDACION = nuevo id, FECHA_LIQUIDADO = ahora.
Para cada pago: insertar en LOG_CUSTODIA: evento = LIQUIDACION, estado_anterior = EN_ADMINISTRACION, estado_nuevo = LIQUIDADO.
Llamar a generarLiquidacionPDF(id_liquidacion).
Actualizar el Dashboard.

5.1 Función: 
cargarCxCPendientes(
)
Esta función es el punto de entrada para la migración de deudas activas. Abre un sidebar HTML donde el usuario puede ingresar o pegar los datos de carga, o importar desde una hoja de Excel/CSV.
Campos requeridos para cada CxC a cargar
ID_CONTRATO: el contrato al que corresponde la deuda (debe existir previamente en la pestaña CONTRATOS).
TIPO_CARGO: ALQUILER / MANTENIMIENTO / PARQUEO / OTRO.
PERIODO_INICIO y PERIODO_FIN: el mes o quincena a la que corresponde la deuda.
FECHA_VENCIMIENTO: la fecha original de vencimiento del cargo.
MONTO_PRINCIPAL: el monto original sin mora.
MONTO_PAGADO: si hubo algún pago parcial antes de la migración, indicarlo aquí. El sistema calculará el saldo.
OBSERVACIONES_MIGRACION: campo libre para anotar el origen del dato ('Sistema anterior', 'Excel de control', etc.).
Lógica que ejecuta la función al cargar cada CxC
Validar que ID_CONTRATO existe en CONTRATOS y está VIGENTE.
Generar ID_CXC automáticamente.
Obtener DIAS_GRACIA del contrato.
Calcular días de mora: 
MAX(
0, HOY - FECHA_VENCIMIENTO - DIAS_GRACIA).
Si días de mora &gt; 0: calcular mora acumulada según el tipo de mora del contrato. Estado = EN_MORA.
Si días de mora = 0 y hay saldo pendiente: Estado = PENDIENTE.
Si MONTO_PAGADO &gt; 0 pero hay saldo: Estado = PARCIAL o EN_MORA según corresponda.
Insertar la fila en CXC_CARGOS con el flag ORIGEN = 'MIGRACION' en OBSERVACIONES.
NO generar recibo PDF ni aviso WhatsApp para los cargos de migración (son históricos).
Actualizar el Dashboard al terminar.
Plantilla de Carga — Pestaña Temporal CARGA_CXC
Claude Code debe crear una pestaña temporal CARGA_CXC con estos encabezados para facilitar el pegado masivo de datos:
ID_CONTRATO | TIPO_CARGO | PERIODO_INICIO | PERIODO_FIN | FECHA_VENCIMIENTO | MONTO_PRINCIPAL | MONTO_PAGADO | OBSERVACIONES_MIGRACION
El menú 'Cargar CxC Pendientes' lee esta pestaña, procesa cada fila y la mueve a CXC_CARGOS. Al terminar, limpia la pestaña de carga y muestra un resumen de lo procesado.
Si una fila tiene error (contrato no existe, fecha inválida, etc.), la marca en rojo y la deja en CARGA_CXC para revisión manual.

cargarPagosSinLiquidar(

9.2 Función: 
verificarIntegridad(
)
Esta función de diagnóstico verifica que el sistema está correctamente configurado y muestra un reporte en el sidebar:
Verificar que todas las pestañas requeridas existen con sus encabezados correctos.
Verificar que los triggers están instalados y activos.
Verificar que la carpeta de Drive para PDFs está configurada y accesible.
Contar registros en cada pestaña y mostrar el resumen.
Verificar que no hay FKs huérfanas (CxC sin contrato, pagos sin CxC, etc.).
Mostrar la versión de Apps Script y el email del propietario del script.
9.3 Manejo de Errores
Toda función debe tener try/catch. Los errores deben loguearse con 
Logger.log(
) y mostrarse al usuario con un toast message o un alert según la gravedad.
Las operaciones críticas (cuadre, liquidación) deben verificar el estado inicial antes de ejecutar y abortar si el estado ya fue procesado (idempotencia).
Si el 
cronDiario(
) falla, debe registrar el error en una celda de CONFIG (ULTIMO_ERROR_CRON) con timestamp para que el administrador pueda diagnosticar.
